---

## 1. Acceptance criteria first

A phase is not done because "a lot of code was written". It is done when every cell of this
table has reproducible evidence behind it (numbers, waveforms, logs, commits).

| Dimension | How it is judged | Evidence form |
|---|---|---|
| Function | A scenario template compiles into an image that runs on the target board | firmware plus serial/network output |
| **Predictability** | The real-time task's dispatch latency has a stated upper bound at p99.9 and max, **and the report is generated by the build together with the artifact** | latency distribution CSV plus report |
| Reliability | Fault injection (out-of-bounds access, stack overflow, plugin crash) does not escape into the real-time plane | fault injection test records |
| Generality | A different scenario template runs **without touching the kernel** | image comparison across two templates |
| **Reproducibility** | Anyone following the README gets the same numbers from scratch | build scripts plus one-command analysis |

> The "predictability" row is where this project separates itself from Zephyr and NuttX:
> **their timing reports are computed afterwards by external tools; ours must be produced by the
> build system alongside the artifact.**

## 3. How each phase is implemented

### P0 — Minimal preemptive scheduler (done)

**Why this comes first**: it is the foundation of the whole project. What has to be verified is
not "can a scheduler run", but "**can interference be attributed cleanly with a self-written
minimal implementation**" — a number measured on someone else's kernel does not transfer.

**Implementation**

| Module | Contents |
|---|---|
| `context.rs` | `#[unsafe(naked)]` + `naked_asm!` for PendSV, **9 instructions**, nothing inserted by the compiler |
| `sched.rs` | Two priorities, SysTick release, `SHPR3` priority configuration |
| `time.rs` | DWT CYCCNT via raw register access (no abstraction overhead in the measured path) |
| `load.rs` | Three loads: Idle (8×nop) / Spin (arithmetic only) / Web (branch-dense + memory writes) |
| `measure.rs` | 8192-sample ring buffer plus CSV output |

**Key decisions**

1. **No FPU anywhere.** The moment a task uses floating point, the hardware does lazy stacking,
   the exception frame grows by S0-S15+FPSCR, `EXC_RETURN` has to change from `0xFFFFFFFD` to
   `0xFFFFFFE9`, and the whole stack layout must be recomputed. Integer-only arithmetic keeps
   the context-switch assumptions simple.
2. **The core metric is `t_start − t_release`**, not execution time. Execution time cannot show
   "how long was it held up".
3. **The resume point sits right next to the timestamp.** The task loop starts with
   `yield_now()`, so the first instruction after resuming is the one that reads the clock.
4. **Run on the 64 MHz HSI, do not configure the PLL.** A misconfigured PLL hangs the chip with
   no output, which is very expensive to debug; and this experiment measures a *relative*
   difference, where the frequency does not change the direction of the conclusion.

**Measured results** (full detail in [`EXPERIMENT-01.md`](docs/EXPERIMENT-01.md) section 7)

| Mode | p50 | p99.9 | max (steady state) |
|---|---|---|---|
| Idle | 229 cyc / 3.58 µs | 234 | 234 |
| Spin | 226 cyc / 3.53 µs | 226 | 235 |
| Web | 234 cyc / 3.66 µs | 234 | 234 |

- Load type affects dispatch latency by ≤ 2.8%, **zero long tail**
- Period jitter peak-to-peak 220 cycles = 3.5 µs
- `max=415~431` comes only from sample 0, a cold-start artefact

**This falsifies the original hypothesis.** The original criterion was "interference above 10%
⇒ the bandwidth cap becomes an architectural cornerstone"; measured interference is about 0%.

But that is **not "the bandwidth cap is unnecessary"** — the experiment never reached the
scenario the cap exists for. The dimensions that actually threaten dispatch latency were not
covered:

| Threat | Why it was not measured | How to measure it |
|---|---|---|
| **Interrupt masking duration** | The load never runs `cpsid i` | Mask interrupts for N cycles inside the load, sweep N |
| **Bus contention** | No DMA, no SPI, no Ethernet traffic | Attach real peripherals at real throughput |
| **Cache jitter** | Cache is off after reset | Re-run with I/D-Cache enabled |
| **Long workloads** | The real-time task only does 32 additions | Scale it up to near the period boundary |
| **Higher clock** | 64 MHz HSI | Configure the PLL to 550 MHz (cache and wait states all change) |

⇒ **The next step is experiment 02: a sensitivity sweep over interrupt-masking duration** (the
independent variable is masking duration, not load type). That is the real criterion for whether
the bandwidth cap is required.

### P1 — Serial CLI and the device API

**What it does**: turns "a device" into something that can be named, addressed and operated.

**Device API (Plan 9 style, non-blocking semantics)**

```
/dev/sensor/<id>/value     read = latest sample snapshot (non-blocking; "not ready" if none)
/dev/actuator/<id>/ctl     write text = submit a command to the real-time plane, ack is async
/etc/<key>                 read-only configuration
/dev/log                   ring buffer; drops the oldest rather than ever blocking
/stat/<task>               read-only runtime snapshot
/ctl/sched/admit           admission control entry point
```

**The key rule**: every write is a **submitted request**, never a direct state change. State
changes are executed by the real-time plane and acknowledged. This is the mechanism that seals
off "Web and plugins are unpredictable" for good.

**Why Plan 9 style rather than classic VFD**: Plan 9's uniformity comes from "per-process
private namespaces + everything controlled through text + one protocol for local and remote". But
its **blocking semantics are unsuitable for hard real-time**, so the uniformity is kept and the
semantics replaced with non-blocking message passing.

**Completion criterion**: `cat /dev/sensor/imu/value` returns within 1 ms;
`echo "start" > /dev/actuator/motor/ctl` takes effect in the next control cycle, and the
real-time plane's timing report is unaffected.

### P2 — Ethernet management plane and the L8 pixel mirror

**What it does**: lets a headless device still be seen.

**Three remote views over one data model**

| View | Transport | Where it is rendered |
|---|---|---|
| Text | serial / WebSocket, plain text lines | PC terminal |
| **Pixel mirror** | L8 indices plus CLUT, dirty rectangles only | PC browser, Canvas lookup |
| Data | JSON state snapshot | PC browser, self-drawn UI |

**Why the pixel mirror is worth building**: L8 transfers a quarter of what RGB565 does, and the
picture is **identical to the device's**, because what travels is the very index data the device
rendered. This channel doubles as a **forensics channel** — every frame's indices can be hashed
and archived.

**Completion criterion**: the browser picture matches the on-device screen pixel for pixel (at
the index level, not by eye); mirroring does not raise the real-time plane's p99.9 latency.

---

### P3 — Display backend

**Why L8 + CLUT**: the reason goes deeper than "saves memory". The palette **is** data and the
screen **is** data — swapping the CLUT reskins the whole UI (RGB565 cannot do this), the
framebuffer can be hashed and diffed (which fits forensics naturally), and the LTDC supports it
in hardware with zero CPU cost.

**Known constraint**: the target ST7789's `COLMOD` offers only 12/16/18 bits, with **no indexed
mode and no CLUT**, so L8 must be expanded to RGB565 before being sent to the panel. This is the
canonical case of "internal representation decoupled from panel format".

**Completion criterion**: dirty-rectangle refresh works (the SPI byte count for a partial
versus full refresh is measurable); a full-screen refresh does not push the real-time plane's
latency past its budget.

---

### P4 — Wasm plugin layer

**What it does**: keeps generality, but with **hard bounds**.

- Runtime (wasmi): Rust, `no_std`, interpreted with no JIT, **built-in fuel metering**,
  linear memory allocated per page ⇒ both execution time and memory footprint are bounded.
- Host ABI: hardware is reachable only through the device API; the plugin plane cannot touch
  real-time plane memory.
- The sandbox lives in the **non-real-time plane**, is bandwidth capped and is preemptible.

**Tiered extensibility**

| Tier | Who writes it | How it gets in | Predictability guarantee |
|---|---|---|---|
| L0 built-in applications | the project itself | compiled into the image | full guarantee |
| L1 scenario configuration | the user | compiled into the image | high (no arbitrary code executes) |
| L2 Wasm plugins | third parties | loaded at run time | **bounded** (fuel + memory pages) |
| L3 native code | anyone | **forbidden** | none |

**Completion criterion**: a malicious wasm (infinite loop, out-of-bounds write, allocation
storm) is stopped by the fuel and memory-page bounds, and the real-time plane's p99.9 and max
**do not move at all**.

---

### P5 — Scenario templates and the build-time schedulability report

**This is where "generality" actually lands**: one declarative file that is simultaneously the
build input, the admission-control basis, and the report input.

```yaml
scene: guard-panel
display: { width: 320, height: 240, format: l8-clut, palette: industrial-dark }
realtime:
  - { task: imu-sample, period: 5ms, deadline: 1ms, budget: 15% }
  - { task: loop-ctrl,  period: 10ms, deadline: 2ms, budget: 10% }
management:
  - { task: http-server, bandwidth: 20% }
extensions:
  wasm_pool: { max_modules: 4, fuel_each: 100000, memory_each: 64KB }
```

**The key point**: what a template produces is still a single image, a single hashable and
signable artifact, a finite and enumerable set of execution paths. Runtime immutability is fully
preserved, but one kernel can serve many scenarios.

**Completion criterion**: swapping the template yields a new scenario **without changing a line
of kernel code**; and when the declared budgets are mathematically impossible, **the build
fails**.

---

### P6 — MPU partitioning and fault injection

**What it does**: turns "reliability" from a design intention into a measurable fact.

- The real-time, display, management and plugin planes are isolated with the MPU (the Cortex-M7
  MPU is optional, and ST implemented it on H7).
- A plugin crash, or malicious code writing memory, cannot reach the real-time plane.

**Completion criterion**: a set of fault injection cases (plugin out-of-bounds write, stack
overflow, divide by zero, fuel exhaustion) all satisfy "the real-time plane keeps running on
time, and p99.9 does not move".

---

### P7 — Verus verification of core invariants

**What it does**: prove only the most central scheduler invariants, not the whole kernel.

Suggested starting set:

1. After a context switch the register state is complete (stack layout and `EXC_RETURN`
   semantics are self-consistent)
2. Priority inheritance is deadlock-free
3. Admission control never exceeds capacity

**Method**: the UCSB retrofit path — adding verification surgically to existing code, rather
than writing proofs before the code exists.

**Completion criterion**: the three invariants pass in CI; the proof artifacts ship with the
repository.

## 4. Cross-phase architectural decisions

| Decision | Reason | Phase |
|---|---|---|
| Scheduler separated from drivers and filesystems | The real-time plane may only touch hardware directly | P6 |
| Every write is a submitted request | Keeps unpredictable inputs outside the real-time plane | P1 |
| L8 is the internal representation, decoupled from panel format | One code path serves L8 hardware panels and RGB565 panels | P2/P3 |
| Fixed application set + compile-time assembly | Generality is not reduced, enumerability is not reduced | P5 |
| CJK fonts subset at build time | Zero parsing cost at run time; a full CJK font costs over 2MB of Flash | P2 |
| A single scenario template file | Avoids the NuttX trap (1500+ Kconfig templates) and the Zephyr trap (Kconfig + Devicetree, two sources of truth) | P5 |

## 5. Risk register

| Risk | Impact | Mitigation | Status |
|---|---|---|---|
| Scope creep | A semester is not enough for four planes | **Strictly serial**; P1–P2 is the backbone | needs continuous discipline |
| Rust preemptive kernel pitfalls | A wrong context switch fails intermittently and is hard to find | Check the disassembly line by line; add canary self-checks | 3 pitfalls hit and documented in P0 |
| Formal verification effort underestimated | P7 slips indefinitely | Only three invariants; retrofit rather than proof-first | not started |
| No ecosystem | The project stays self-referential | L2 plugin plane is the ecosystem entry point; publish early | open |
| Only one board | Interrupt and multi-core testing are limited | All experiments are single-core friendly | known |
| STM32H7 D-Cache vs DMA coherency | Screen corruption, random crashes | Mark the framebuffer Non-Cacheable; put DMA buffers in AXI SRAM, never DTCM | recorded in the hardware notes |
| WFI conflicts with the debug port | Cannot debug a sleeping system | Root cause of the failed `DBG_SLEEP` workaround still unknown | **unresolved** |

## 6. Explicit non-goals

Written down to prevent scope creep:

- No full POSIX (no `fork`, no `mmap`, no complete signal semantics)
- No chasing driver breadth
- No full-kernel formal verification
- No runtime loading of native code
- No SMP (single core first)
- No Linux compatibility layer
- No graphical UI framework at this stage (L8 pixels plus simple widgets only)

## 7. What comes next

Experiment 02 is done (2026-11-22) and it changed what the next step should be.

**What it established**: worst-case release delay grows 1:1 with interrupt-masking duration
(99.4 %–100.6 % across seven stages), while the context-switch cost stays flat at 267 cycles.
Masking beyond one period destroys phase lock outright (`tick_missed = 64`, `phase` uniform).

**What that implies**: the bandwidth cap is not the mechanism that protects against this. Nothing
in rate limiting stops a driver holding `cpsid i`. The guarantee that matters is **an upper bound
on interrupt-masking duration, enforced at build time** — and that is a static property, which
makes it far more tractable than runtime admission control.

So the order changes:

1. ✅ **Interrupt-masking budget as a build-time check** — done 2026-11-22. A manifest declares
each critical section's budget; the build fails when a declaration exceeds the allowance; a
runtime monitor compares measured against declared. See [`docs/MASK-BUDGET.md`](docs/MASK-BUDGET.md).
   It caught two of my own mis-declarations within the hour.
2. ✅ **Experiment 03: re-run with cache enabled** — done 2026-11-22. The constant falls
   283 → 122 cycles (−57 %), the 1:1 slope does not move. Confirms the masking rule is structural
   and needs no per-configuration calibration. See [`docs/EXPERIMENT-03.md`](docs/EXPERIMENT-03.md).
3. **Configure the PLL to 550 MHz and re-run** — the remaining unknown. The absolute cycle counts
   cannot be extrapolated, and the 57 % cache benefit is likely *larger* there because flash wait
   states dominate more. The 1:1 slope should survive, but that is a prediction, not yet a
   measurement.

With the PLL run done, the remaining unknown is the target frequency, and the P5 template schema
can be settled.

## Appendix B: The pitfalls hit so far

The code-level pitfalls that **fail silently** are all written up in `exp/README.md`. Only the
conclusions are repeated here:

| Pitfall | Consequence | Lesson |
|---|---|---|
| SHPR3 bit fields swapped | HardFault on the first interrupt (INVPC) | Register bit fields must be looked up, never recalled from memory |
| `wfi` kills the SWD debug port | probe-rs reports a FAULT response and even CPUID cannot be read | Debug clock behaviour in Sleep has to be considered |
| RTT defaults to `NoBlockSkip` | 8192 samples silently became 5690, **with no error at all** | Output channel reliability must be verified, not assumed |
| probe-rs prefixes RTT output with a timestamp | parse.py silently skipped every sample | Every stage of the data pipeline needs its own verification |

**The common lesson**: three of these four fail silently — no error, and the data simply looks
like that. So this project's evidence rule is: **every claim must come with output somebody else
can re-check, not just a conclusion.**
