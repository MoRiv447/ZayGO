# 实验 03：开启 L1 缓存后的复测

> 中文版。 [English version](EXPERIMENT-03.md)
>
> **状态：2026-11-22 已上板跑通。** 三档配置（全关 / 只开 I-Cache / I+D-Cache），
> 同一套屏蔽扫描，各 1024 个样本。
> 结论：**缓存把常数砍掉 57%，斜率一点没动。**

---

## 一、问题

实验 01 与 02 都是在**缓存全关**下跑的，因为那是 STM32H7 的复位默认值（DM00272913）。
真实产品会打开它们。

后果有两种可能，而对架构来说意义完全不同：

| 如果缓存… | 那么 |
|---|---|
| 改变了屏蔽关系的**斜率** | 1:1 的预算规则就依赖缓存配置，每种配置都得单独标定 |
| 只改变了**常数** | 1:1 是结构性的；只需为每种配置重测固定开销 |

实验 02 的局限一节已经预判是第二种。这个实验就是去检验它。

---

## 二、方法

三个构建，同一份固件，只有 `CACHE_MODE` 不同：

| 模式 | I-Cache | D-Cache |
|---|---|---|
| `Off` | ✗ | ✗ |
| `I` | ✓ | ✗ |
| `ID` | ✓ | ✓ |

每次跑完整的 8 档屏蔽扫描（每档 128 样本）。`I` 对 `Off` 的差隔离出**取指**的贡献，
`ID` 对 `I` 的差隔离出**数据访问**的贡献。

### 先必须解决的那个 D-Cache 问题

开 D-Cache 会让 RTT 输出**静默失效**。

RTT 的原理是把字符写进 RAM 里的环形缓冲，probe-rs 通过 SWD **直接从 RAM 读**。
D-Cache 一开，这些写入变成 cache 里的脏行，probe-rs 读到的是旧 RAM。
表现是输出莫名缺行或乱序，**任何地方都不报错**。

修法是只在输出路径上放弃缓存：

```rust
fn stop_tick() {
    /* 停 SysTick */
    // 把整个 D-Cache 写回 RAM，然后关掉。
    // ARM 要求先 clean 再 disable：只清使能位会留下未写回的脏行，
    // 那些数据就此丢失（在 M7 上是"行为不可预测"，不是自动写回）。
    cache::prepare_for_rtt();
}
```

采样期带缓存，dump 期不带。dump 不在测量路径上，跑慢一点没有代价。

clean/invalidate 的循环从 `CCSIDR` 读组数与路数，不写死 16KB/4way ——
写死的循环换一颗芯片就会只清一半，而且不会报错。

## 三、结果

平台：STM32H723ZGT6（Cortex-M7 r1p2），64 MHz HSI，未配 PLL，周期 1 ms。
每档 128 样本，`overruns = 0`。

各屏蔽时长下的 `phase` p50：

|---|---|---|---|---|---|---|
| 0 | 399 | 256 | **170** | 283 | 197 | **122** |
| 500 | 918 | 758 | **671** | 283 | 197 | **122** |
| 1000 | 1407 | 1262 | **1175** | 283 | 197 | **122** |
| 2000 | 2400 | 2263 | **2175** | 283 | 197 | **122** |
| 4000 | 4419 | 4261 | **4175** | 283 | 197 | **122** |
| 8000 | 8419 | 8262 | **8175** | 283 | 197 | **122** |
| 16000 | 16410 | 16261 | **16175** | 283 | 197 | **122** |

## 四、判读

### 4.1 斜率纹丝不动

每一档配置都落在 100.0%~100.6%。**1:1 是结构性的，不是微架构性的** ——
正是实验 02 预判的那样。

这在工程上很重要：屏蔽预算规则不需要为每种缓存配置单独标定。一条规则，一个数。

### 4.2 常数动得很厉害，而且几乎各占一半

`dispatch` 从 283 → 197 → 122 周期，总共降 57%。

| 步骤 | 省下的周期 | 占总降幅 |
|---|---|---|
| Off → I | 86 | 53% |
| I → I+D | 75 | 47% |

取指与数据访问几乎等分。只报"开 I+D 省了 161 周期"会把这件事藏起来 ——
这就是为什么多跑两次做三档拆分是值得的。

剩下那 122 周期，是这条切换路径在 64 MHz 下的地板：异常入口、PendSV、`schedule`、
任务入口、一次 `CYCCNT` 读。

### 4.3 基线 `phase` 降得比 `dispatch` 多

399 → 170 是 −229，而 `dispatch` 只能解释其中 −161。多出的 −68 来自激励路径本身
（`mask_round` 的等待循环与回绕检测）也在从缓存里取指。

这提醒一件事：`phase` 和 `dispatch` 不是"同一个数加一个常数"，两者构成不同，
而它们的差值在配置之间变化了 68 周期。

### 4.4 对预算机制的后果

[`MASK-BUDGET.md`](MASK-BUDGET.md) 里的中断屏蔽预算以**屏蔽周期数**表达，
这个数不受缓存影响。很好 —— 规则能跨配置成立。

但 `max_mask_cycles = 800` 是按 64000 周期的一个比例取的，而**总**释放延迟是
`dispatch + mask`。开了缓存之后固定部分从 283 降到 122，同样的屏蔽预算留下了更多余量。
诚实的说法是：

> 屏蔽预算与缓存无关；但它导致的最坏延迟不是。

## 五、局限

1. **本芯片两颗 L1 缓存都是 16KB / 32 字节行**，而工作负载相对它们极小。
   会颠簸缓存的负载表现会不同；本实验没有刻画驱逐行为。
2. **没有 MPU 配置。** [`HARDWARE-NOTES.md`](HARDWARE-NOTES.md) 里帧缓冲/DMA 一致性的问题
   完全没被触及，那属于 P6。
3. **dump 路径按设计是关缓存的。** 这是为 RTT 可见性做的有意让步，不是意外。
4. **64 MHz。** 绝对周期数是复位默认时钟下的结果。57% 的降幅在 550 MHz 上很可能更大，
   因为那时 flash 等待周期占的比重高得多 —— 但这是推测，不是测量。
5. **`96000` 仍是相位失锁那一档**，它的 p50（约半周期）不是延迟值，不应跨配置比较。
